# Functional Programming

## Make illegal states unrepresentable

Coined by Yaron Minsky; [Wlaschin, Designing with types](https://fsharpforfunandprofit.com/posts/designing-with-types-making-illegal-states-unrepresentable/):

> All three cases are explicitly represented, and the fourth possible case [...] is not allowed.

Stacking independent optional fields or booleans (coined: flag-stacking) leaves illegal combinations constructible. Model domains with algebraic data types (sum and product types, [Haskell 2010 Report](https://www.haskell.org/onlinereport/haskell2010/haskellch4.html) §4.2.1), exhaustive pattern matching, total functions, and parametric polymorphism; parse into precise types once at the boundary.

## Data shape dictates function shape

From the [HtDP design recipe](https://htdp.org/2023-8-14/Book/part_one.html):

> The design recipe has two dimensions. One concerns the process of design [...] The other explains how the chosen data representation influences the design process.

> A good programmer designs programs. A bad programmer tinkers until the program seems to work.

Define the data variants before the function: one branch per variant, structural recursion where the data is self-referential, and a wish list of pure helpers (name, signature, one-line purpose).

## Compose small pure functions over immutable values

From [Hughes, Why Functional Programming Matters](https://www.cs.kent.ac.uk/people/staff/dat/miranda/whyfp90.pdf) (*The Computer Journal* 32(2), 1989):

> The ways in which one can divide up the original problem depend directly on the ways in which one can glue solutions together. Therefore, to assist modular programming, a language must provide good glue.

Glue small pure functions over immutable values with higher-order combinators (`map`, `filter`, `fold` / `reduce`, `flatMap`) and composition instead of monolithic stateful loops.

## Functional core, imperative shell

Follow [Bernhardt, Functional Core, Imperative Shell](https://www.destroyallsoftware.com/screencasts/catalog/functional-core-imperative-shell) (screencast summary): keep branching and domain rules in a pure value-in/value-out core, and push I/O, mutation, time, and randomness to a thin outer shell. Unobservable local mutation preserves referential transparency; avoid free monads or effect ASTs unless you need multiple interpreters. Keep operations orthogonal with no hidden cross-state coupling ([Raymond, The Art of Unix Programming](http://www.catb.org/esr/writings/taoup/html/ch04s02.html), ch. 4), and hide change-prone decisions behind narrow module boundaries ([Parnas, On the criteria to be used in decomposing systems into modules](https://doi.org/10.1145/361598.361623), CACM 1972).

## Equational reasoning and semantic lowering

From [Leroy, Formal verification of a realistic compiler](https://xavierleroy.org/publi/compcert-CACM.pdf), CACM 52(7), 2009, §1:

> Compilers are generally assumed to be semantically transparent: the compiled code should behave as prescribed by the semantics of the source program.

Every rewrite must preserve semantics across all valid inputs, evaluation order, cancellation, and lifetimes. When lowering constructs ($C$) into core primitives ($P$) under composition operators ($K$), every $c \in C$ needs a finite lowering into the [subuniverse generated by P](https://www.math.uwaterloo.ca/~snburris/htdocs/UALG/univ-algebra2012.pdf) (§II.3, Def. 3.1); never drop a primitive unless remaining primitives express it or the owner signs off.

## Gotchas

- Extract typeclasses or higher-kinded abstractions only after several concrete types share the shape.
- In hot loops, keep functional structure without per-iteration closure or combinator allocations.
- Keep fault recovery in an external supervisor rather than inside pure domain types.
